## Порядок выкладки

Сначала миграция, потом функции, потом слияние PR. Так функции и сайт не
обращаются к таблицам, которых ещё нет.

1. Проверь, что миграция ещё не применена, и что последняя применённая — `20261011120000_previews_feedback`:

   ```bash
   supabase migration list
   ```

2. Примени миграцию (один файл, повторный прогон безопасен):

   ```bash
   supabase db push
   ```

3. Проверь права: выполни по запросам `supabase/audit/recovery_tags_audit.sql` в SQL Editor.
   Ожидаемое написано рядом с каждым пунктом:
   - пункт 1: три строки `true`;
   - пункты 2 и 3: пусто (у `anon` и `authenticated` нет прямого доступа к таблицам);
   - пункт 4: `recovery_code_set`, `recovery_code_consume`, `recovery_code_confirm` — `anon=false authenticated=false service_role=true`;
     `tags_all`, `my_recovery_code_state`, `owner_tag_*`, `owner_user_set_tag` — `anon=false authenticated=true`;
     помощники `tags_limit`, `tag_clean_name`, `tag_clean_color`, `tag_json`, `require_owner` — всё `false`;
   - пункт 5: у всех `search_path=""`;
   - пункты 6 и 7: `0` (в `recovery_codes` только хеши, все цвета тегов в формате `#rrggbb`).

4. Задеплой **все четыре функции аккаунтов**. Менялся общий код `_shared/accountsCore.ts`
   и `accountsDeps.ts`: `register` теперь выдаёт код, `account` создаёт и подтверждает его,
   `recovery-request` умеет вход по коду. `admin-users` собирается из того же общего кода,
   поэтому его тоже стоит обновить, чтобы все функции были одной версии:

   ```bash
   npx supabase@latest functions deploy register --no-verify-jwt --use-api
   npx supabase@latest functions deploy account --no-verify-jwt --use-api
   npx supabase@latest functions deploy recovery-request --no-verify-jwt --use-api
   npx supabase@latest functions deploy admin-users --no-verify-jwt --use-api
   ```

   `admin-content` не менялась. Секреты не добавляются: код хешируется тем же
   `ACCOUNTS_HASH_SECRET` (или, если его нет, service-ключом), что и лимиты. **Не меняй этот секрет**
   после выкладки: хеши уже созданных кодов перестанут подходить, а людям придётся создать код заново.

5. Слей PR в `main`. Деплой соберёт сайт сам.

Если сайт выложился раньше функций, ничего не ломается, но новый экран кода после регистрации
не появится, пока `register` не обновлена (старая функция код не выдаёт).

## Код восстановления: как это работает

- Код вида `XXXX-XXXX-XXXX-XXXX`: 16 символов из 32 без похожих (нет 0, 1, I, O), около 80 бит. Перебрать его нельзя.
- В базе хранится только HMAC-хеш (привязан к пользователю), открытого кода нет нигде, кроме экрана
  у самого человека. Таблица `recovery_codes` закрыта от сайта; состояние («есть ли код, когда создан,
  сохранён ли») отдаёт функция `my_recovery_code_state`, хеша в ответе нет.
- **После регистрации** показывается экран с кодом: «Скопировать» и «Я сохранил». «Я сохранил» доступно
  после копирования (или если отметить, что код записан вручную). Пока код не подтверждён, сайт
  не пускает на другие страницы. Если страницу обновили до подтверждения, выдаётся новый код.
- **Уже зарегистрированным:** «Настройки» → «Код восстановления» → «Создать код восстановления»
  (нужен текущий пароль). Новый код отменяет старый.
- **Забыл пароль:** «Забыли пароль?» → «У меня есть код» → ник, код, новый пароль. Подошёл: пароль
  меняется, код сгорает (удаляется одним запросом, повторно не сработает), все сеансы завершаются,
  человек входит с новым паролем, и ему предлагают создать новый код (можно «Позже»).
- **Защита от перебора:** капча Turnstile, не больше 10 попыток в час с одного IP и 5 в час на ник
  (считается каждая попытка, верная или нет, и независимо от того, есть ли такой ник). Ответ при неверном
  нике и при неверном коде одинаковый: «Неверный ник или код».
- Заявки на восстановление через админку остаются запасным вариантом («У меня нет кода» на той же странице).

## Теги: как это работает

- У человека один тег или ни одного. Тег только значок рядом с ником, прав он не даёт:
  права по-прежнему берутся из роли в `auth.users`.
- Значок виден везде, где виден ник: профиль и настройки, «Друзья» и список пользователей, комнаты,
  лента, плейлисты, меню профиля, админка.
- Владелец в админке: «Люди» → «Теги» (создать, переименовать, перекрасить, удалить) и выбор тега в карточке
  пользователя. Название до 20 символов, цвет выбирается цветовым пикером. Формат `#RRGGBB` проверяет база.
- Цвет текста на значке (белый или чёрный) подбирается автоматически по контрасту с фоном.
- Изменение названия и цвета видно у всех при очередном обновлении справочника (раз в минуту и когда вкладка
  снова на экране, либо сразу при перезагрузке страницы). Удаление тега снимает его со всех.
- Писать теги можно только функциями с проверкой `is_owner()`: админ получает «Нет доступа». Читать справочник
  могут все вошедшие (`tags_all`), аноним нет.

## Что проверить руками

1. **Регистрация.** Зарегистрируй тестовый аккаунт: должен появиться экран с кодом. «Я сохранил» недоступно, пока
   не нажато «Скопировать». Попробуй перейти на другую страницу: вернёт на экран кода. Нажми «Скопировать»,
   вставь код в заметку, «Я сохранил»: сайт откроется.
2. **Вход по коду.** Выйди. «Забыли пароль?» → «У меня есть код», введи ник, код (строчными и без дефисов тоже
   подойдёт) и новый пароль. Должно открыться предложение создать новый код. В другой вкладке под этим же
   аккаунтом сеанс завершится при ближайшем обновлении токена (до часа).
3. **Одноразовость.** Тем же кодом ещё раз: «Неверный ник или код». Неверный ник и неверный код дают один и тот же ответ.
4. **Старые аккаунты.** В «Настройках» → «Код восстановления» → создать код (с паролем). Создай ещё один: прежний
   перестанет работать.
5. **Перебор.** 6 неверных попыток подряд на один ник: дальше «Слишком много попыток», даже с верным кодом (через час снова можно).
6. **В базе** (SQL Editor): `select user_id, left(code_hash, 8), confirmed from public.recovery_codes;`: видны только хеши.
7. **Теги.** В админке под владельцем: «Люди» → «Теги» → создай тег и выбери цвет (светлый и тёмный: текст на
   значке меняется на чёрный и белый). В «Пользователи» открой карточку, выбери тег. На сайте тег виден рядом с ником в
   профиле, «Друзьях», ленте, комнате. Переименуй тег или перекрась: у остальных обновится после перезагрузки
   страницы. Удали тег: он пропадёт у всех.
8. **Админ (не владелец).** Раздела «Теги» нет, в карточке пользователя нет выбора тега.

## Аудит прав на новые таблицы и функции

- `recovery_codes`, `user_tags`, `user_tag_assignments`: RLS включён, политик нет, права у `anon` и
  `authenticated` отозваны, полный доступ только у `service_role`.
- Функции кода (`recovery_code_set`, `recovery_code_consume`, `recovery_code_confirm`) доступны только
  `service_role`, то есть Edge Functions; сайт и админка их вызвать не могут.
- `my_recovery_code_state`, `tags_all`: только вошедшим (`require_active_user`), забаненный и аноним получают отказ.
- `owner_tag_create`, `owner_tag_update`, `owner_tag_delete`, `owner_user_set_tag`: открыты `authenticated`,
  но внутри `require_owner()`: админ и обычный пользователь получают «Нет доступа».
- Цвет проверяется в трёх местах: в функции (`tag_clean_color`), в `check` таблицы и на сайте перед подстановкой в стиль.
- Все функции `security definer` с `search_path = ''`. Внутренние помощники закрыты от сайта.
- Названия тегов и коды выводятся интерполяцией Vue (с экранированием).

(`src/admin/lib/__tests__/accountsFunctions.test.ts`, `recoveryCode.test.ts`) и аудит-скрипт.
