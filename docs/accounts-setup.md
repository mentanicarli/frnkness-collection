# Запуск аккаунтов (этап 2): пошаговая инструкция

Что появится: вход по нику и паролю, регистрация с капчей, «мягкая стена»
(без входа видна только заставка), профиль и настройки, заявки «Забыли
пароль?», в админке — «Пользователи» и «Заявки на восстановление».

**Главное правило порядка:** сначала база, функции и твой аккаунт
владельца, потом проверка на своём компьютере, и только потом мерж (сайт
обновляется сам после мержа). Так ты не окажешься снаружи админки.

| Шаг | Что делаем | Где |
|---|---|---|
| 1 | Капча Cloudflare Turnstile: два ключа | dash.cloudflare.com |
| 2 | Публичный ключ — в код сайта | файл `src/supabaseConfig.ts` |
| 3 | Миграции, секреты, функции | терминал |
| 4 | Настройки входа и почты в Supabase | панель Supabase |
| 5 | Ники и роли тебе и другу | Supabase → SQL Editor |
| 6 | Проверка на своём компьютере | `npm run dev` |
| 7 | Мерж и проверка frnkness.ru | говоришь мне «да» |
| — | Аварийный выход | Supabase → SQL Editor |

Между шагами 3 и 7 живой сайт frnkness.ru работает на старом коде. В эти
минуты у гостей не засчитываются прослушивания и пустой чарт (база уже
пускает к статистике только вошедших). Поэтому шаги 3–7 лучше пройти
за один подход. Открытая сейчас админка продолжит работать, но заново
войти в старую админку по email после шага 5 уже не получится — только в
новую, по нику (шаг 6).

## Шаг 1. Cloudflare Turnstile (капча, бесплатно)

Turnstile работает на любом сайте, переносить домен в Cloudflare не нужно.

1. Открой <https://dash.cloudflare.com/sign-up>, зарегистрируйся (почта +
   пароль), подтверди почту по письму.
2. В левом меню панели найди **Turnstile** (может быть внутри раздела
   «Application security» / «Protect & Connect»; можно ввести «Turnstile» в
   поиск панели).
3. Нажми **Add widget**:
   - **Widget name** — `frnkness`;
   - **Hostname management** → добавь два адреса: `frnkness.ru` и
     `localhost` (localhost нужен для проверки на своём компьютере на шаге 6);
   - **Widget mode** — **Managed** (обычно люди просто видят галочку);
   - **Pre-clearance** — не трогай (выключено).
4. Нажми **Create**. Появятся два ключа:
   - **Site Key** (публичный, начинается с `0x…`) — пойдёт в код сайта, его
     можно показывать кому угодно;
   - **Secret Key** (секретный) — только в секреты функций Supabase (шаг 3).
     Никуда больше его не вставляй и не присылай в чат.

Потерял секретный ключ — открой виджет → **Settings**, там можно посмотреть
или перевыпустить ключ (после перевыпуска повтори команду из шага 3.3).

## Шаг 2. Публичный ключ — в код сайта

Пришли мне **Site Key** — я впишу его и закоммичу в ветку `feature/accounts`.

Если хочешь сам: открой `src/supabaseConfig.ts`, найди строку

```ts
const DEFAULT_TURNSTILE_SITE_KEY = ''
```

и вставь ключ между кавычками: `const DEFAULT_TURNSTILE_SITE_KEY = '0x4AAAA…'`.
Без ключа регистрация и «Забыли пароль?» показывают «Капча не настроена».

## Шаг 3. База, секреты и функции (терминал)

Терминал — в папке проекта, ветка `feature/accounts`. Supabase CLI
запускается через `npx` (как в docs/admin-setup.md).

### 3.1. Подключиться к проекту

```bash
npx supabase@latest login
```

```bash

```

### 3.2. Миграции

Сначала посмотреть, что будет применено (ничего не меняет):

```bash
npx supabase@latest db push --dry-run
```

Должно быть три новые миграции:
`20261006120000_accounts.sql`, `20261006120100_accounts_admin.sql`,
`20261006120200_accounts_sql_helpers.sql`. Если в списке есть что-то ещё —
остановись и пришли мне вывод. Если всё так — применить:

```bash
npx supabase@latest db push
```

Миграции заодно закрывают найденное аудитом: таблицу `play_counts_backup`
(раньше её мог читать и менять кто угодно), лишние права у анонима и права
по умолчанию на новые таблицы.

### 3.3. Секреты функций

Сгенерируй случайный секрет для хешей IP (лимиты регистраций и заявок):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Запиши оба секрета: вместо `ВСТАВЬ_SECRET_KEY` — Secret Key из Turnstile,
вместо `ВСТАВЬ_СЛУЧАЙНУЮ_СТРОКУ` — строку из команды выше:

```bash
npx supabase@latest secrets set TURNSTILE_SECRET_KEY=ВСТАВЬ_SECRET_KEY ACCOUNTS_HASH_SECRET=ВСТАВЬ_СЛУЧАЙНУЮ_СТРОКУ
```

Проверить, что секреты на месте (покажет только имена и хеши):

```bash
npx supabase@latest secrets list
```

### 3.4. Функции

Пять команд по очереди (`admin-content` тоже обновилась: теперь пускает и
владельца, а правки подписывает ником):

```bash

```

```bash
npx supabase@latest functions deploy admin-users --no-verify-jwt --use-api
```

```bash

```

```bash

```

```bash

`--no-verify-jwt` — нормально и нужно: вход проверяют сами функции (иначе
браузер не пройдёт предварительный CORS-запрос, а регистрация и «Забыли
пароль?» работают без входа).

```

## Шаг 4. Настройки Supabase: вход и почта

Панель Supabase → проект → **Authentication**. Названия пунктов в панели
иногда меняются — ищи по смыслу.

### 4.1. Способы входа (**Sign In / Providers**)

- **Allow new users to sign up** — **выключено** (уже так). Регистрация идёт
  только через нашу функцию с капчей.
- **Email** — **включён** (через него работает вход по паролю; почта при
  этом не используется).
- **Confirm email** — **включено**. Тогда смена адреса аккаунта требует
  подтверждения письмом, а письма не уходят (4.3), поэтому сменить адрес в
  обход сайта нельзя.
- **Phone**, **Anonymous sign-ins**, все соцсети (Google, GitHub и т. п.) —
  **выключены**.
- **Allow manual linking** — выключено.

В настройках провайдера **Email** (раскрой его):

- **Secure email change** — **включено**;
- **Secure password change** — **включено**: сменить пароль в обход сайта
  (без текущего пароля) нельзя, если вход был давно.

### 4.2. Почему важна почта

Технический адрес аккаунта (`u-…@id.frnkness.ru`) считается из ника, и узнать
его может кто угодно. Без защиты можно было бы дёргать «сброс пароля»,
«вход по ссылке» и «повторное письмо» на эти адреса. Письма уходили бы в
несуществующие ящики, а частые возвраты Supabase наказывает ограничением
почты для проекта. Защита в три слоя:

1. **Не настраивай свой SMTP** (Authentication → Emails → SMTP Settings — пусто).
   Встроенная почта Supabase шлёт письма только участникам команды проекта,
   на чужие адреса не отправляет вовсе.
2. У домена `id.frnkness.ru` нет почтовых записей (MX). Supabase проверяет их
   перед отправкой и такие адреса обычно отбраковывает. Не создавай для
   этого домена почту.
3. **Хук отправки писем** (4.3) — заменяет любую отправку «ничем».
   Это гарантия, даже если кто-то потом настроит SMTP.

### 4.3. Хук: письма не отправляются никогда

**Authentication → Hooks** (Auth Hooks) → **Add hook** → **Send Email hook**:

- тип — **Postgres**;
- схема — `public`;
- функция — `auth_hook_send_email_noop`;
- включить (**Enable**) и сохранить.

После этого в **Rate Limits** становится редактируемым лимит писем — поставь
его поменьше (например, 2 в час): писем всё равно не будет.

### 4.4. Лимиты (**Rate Limits**)

- **Sign-ups and sign-ins**: оставь как есть (30 за 5 минут с одного IP). Это
  и есть лимит попыток входа по нику.

## Шаг 5. Ники и роли тебе и другу (SQL Editor)

1. Открой файл `supabase/setup/accounts_owner.sql` в редакторе, скопируй
   **целиком** в Supabase → **SQL Editor**.
2. В блоке `VALUES` замени четыре значения:
   - `ТВОЙ_EMAIL@example.com` — email, с которым ты сейчас входишь в админку;
   - `ТвойНик` — твой новый ник (например, `frnkness` — его стоит занять сразу);
   - `EMAIL_ДРУГА@example.com` и `НикДруга` — то же для друга.

   Ник: 3–20 символов, русские и латинские буквы, цифры, `_`, `.`, `-`.
3. Нажми **Run**. Внизу должна появиться таблица из двух строк: твой ник с
   ролью `owner` и ник друга с ролью `admin`.

Если вместо таблицы ошибка («Ник … не подходит», «Не найден аккаунт…»),
ничего не изменилось — исправь значение и запусти снова. Повторный запуск
после успеха тоже безопасен.

Пароли остаются прежними: дальше ты входишь **ником** и старым паролем.
Передай другу его ник (пароль у него тот же).

## Шаг 6. Проверка на своём компьютере

Ветка `feature/accounts`, в терминале:

```bash
npm run dev
```

Открой адрес, который покажет команда (обычно <http://localhost:5173>).
Сайт работает с настоящей базой Supabase.

1. **Стена.** Открой <http://localhost:5173/#/track/zlaya-nostalgia/makanochki> —
   должна открыться заставка. Нажми «Войти», введи **свой ник** и пароль —
   откроется тот же трек.
2. **Ошибка входа.** Выйди (аватар справа вверху → «Выйти»). Попробуй неверный
   пароль, потом несуществующий ник — оба раза «Неверный ник или пароль».
3. **Админка.** Войди снова и открой <http://localhost:5173/admin.html> (или
   аватар → «Админка») — должна открыться **без повторного входа**. В меню
   есть «Пользователи» и «Заявки» (их видит только владелец).
4. **Регистрация.** В другом браузере (или окне инкогнито) открой
   <http://localhost:5173>, зарегистрируй тестовый ник, например `тест_проверка`.
   Капча должна появиться и пройти. После регистрации открывается сайт.
5. **«Нет доступа».** В том же окне открой <http://localhost:5173/admin.html> —
   должно быть «Нет доступа».
6. **Заявка.** Выйди в этом окне, нажми «Забыли пароль?», отправь заявку на
   тестовый ник. В своей админке → «Заявки» она появится; задай временный
   пароль, войди им в тестовый аккаунт — сайт попросит придумать новый.
   Закрой заявку («выполнена») — контакт исчезнет.
7. **Уборка.** В админке → «Пользователи» → тестовый ник → «Удалить» (введи
   ник для подтверждения).

Всё так — переходим к мержу. Что-то не так — не мержим, пришли мне, что
видишь (скриншот и текст ошибки).

## Шаг 7. Мерж

Скажи мне «да» — я волью `feature/accounts` в `main` и отправлю на GitHub.
Сайт соберётся и опубликуется сам (несколько минут, видно в GitHub → Actions).

После публикации:

1. Открой <https://frnkness.ru> — заставка; войди ником.
2. Открой <https://frnkness.ru/admin.html> — админка без повторного входа.
3. GitHub → **Actions** → **Supabase keepalive** → **Run workflow** — запуск
   должен стать зелёным. Дальше он сам запускается раз в 3 дня. Он берёт
   секреты `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, которые уже есть
   для деплоя.
4. По желанию: в Cloudflare → Turnstile → виджет → **Settings** убери
   `localhost` из адресов (Cloudflare советует не держать его в боевом
   виджете). Понадобится снова — добавишь.
5. Dependabot сам начнёт присылать pull request с обновлениями раз в неделю.
   Их проверяет `CI` (зелёная галочка), сайт они не трогают, пока ты не
   смержишь.

## Аварийный выход

Всё делается в Supabase → **SQL Editor** из файла
`supabase/setup/accounts_emergency.sql`. В нём пронумерованные блоки:
копируешь файл в редактор, **выделяешь мышкой один нужный блок** и
нажимаешь **Run** — выполнится только выделенное.

- **Блок 0 — кто есть кто:** ники, роли, баны, технические адреса.
- **Блок 1 — вернуть себе роль владельца и снять бан:** подставь свой ник.
- **Блок 2 — задать новый пароль и завершить все сеансы:** подставь ник и
  новый пароль. Пароль сохраняется только хешем; запрос потом можно удалить
  из истории SQL Editor.
- **Блок 3 — не помню ник:** смотри блок 0. Если у аккаунта нет ника,
  запусти заново `accounts_owner.sql`, указав вместо старого email
  технический адрес из блока 0.

Владельца нельзя удалить, понизить или забанить ни из админки, ни из
функций — это держит триггер в базе. Блоки 1–2 обходят его строкой
`set local app.owner_override = 'on'` (действует только внутри этого
запуска).

Если после мержа сайт сломался совсем — скажи мне: откачу код коммитом
`git revert` (база при этом остаётся новой, вход — по нику).

### Секреты функций (Supabase → Edge Functions → Secrets)

| Секрет | Зачем |
|---|---|
| `TURNSTILE_SECRET_KEY` | Проверка капчи на сервере. Без него регистрация и заявки отклоняются |
| `ACCOUNTS_HASH_SECRET` | Хеши IP и ников для лимитов (сам IP не хранится) |
| `GITHUB_TOKEN`, `BLOB_SIGNING_KEY` | Как раньше — для `admin-content` (docs/admin-setup.md) |

### Лимиты

- Регистраций с одного IP — 10 в сутки (компания в одной сети уложится).
- Заявок «Забыли пароль?» — 3 в сутки на ник и 3 на IP; сверх лимита форма
  отвечает так же, но заявка не создаётся.
- Проверок пароля (смена пароля, удаление аккаунта) — 10 в час на аккаунт.
- Попыток входа — встроенный лимит Supabase (шаг 4.4).
